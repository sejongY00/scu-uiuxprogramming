# 캠퍼스 분실물

교내에서 잃어버린 물건과 주운 물건을 한곳에서 올리고 찾아가는 서비스 웹페이지입니다. 7주차에는 사용자가 **분실·습득 제보를 시작부터 완료까지 직접 마칠 수 있는 단계별 흐름**을 구현했습니다.

- 배포 주소: https://sejongy00.github.io/scu-uiuxprogramming/
- GitHub 저장소: https://github.com/sejongY00/scu-uiuxprogramming

## 서비스 개요

| 항목 | 내용 |
| --- | --- |
| 주요 사용자 | 교내에서 물건을 잃어버렸거나 주운 학생·교직원 |
| 서비스 목적 | 잃어버린 사람과 주운 사람의 제보를 한곳에 모아, 물건이 주인에게 돌아가게 한다 |
| 사용자 목표 | 잃어버린(또는 주운) 물건을 제보하고, 접수되었는지 확신한다 |
| 핵심 행동 | ‘단계별 제보’에서 제보 종류·물건 정보·장소·날짜·이메일을 입력하고 내용을 확인해 제보를 완료한다 |
| 완료 조건 | 확인 화면에서 ‘제보 완료하기’를 눌러 접수번호(`LF-001` 형식)가 보이는 완료 화면에 도달한다 |

기존 기능(서비스 소개, 주요 기능 탭 3개, 테마 전환, 이메일만 남기는 빠른 제보)은 그대로 유지하고, 같은 `index.html`·`style.css`·`script.js`에 흐름을 이어서 추가했습니다.

## 사용자 흐름

헤더 메뉴의 ‘단계별 제보’ 또는 ‘제보 시작하기’ 버튼으로 진입합니다. 입력 단계 2개, 확인 1개, 완료 1개로 모두 4단계입니다(5단계 이내).

```
제보 시작하기
   ↓
1/3 물건 정보   : 제보 종류(분실/습득) · 물건 분류 · 물건 특징      ← 모두 필수
   ↓
2/3 장소·연락   : 건물 · 상세 장소(선택) · 날짜 · (습득이면) 맡겨 둔 곳 · 이메일
   ↓
3/3 제보 확인   : 입력값 목록. 항목별 ‘수정’, 이전 버튼으로 돌아가 고칠 수 있음
   ↓
완료            : 접수번호와 접수 문구, 입력 내용 요약. ‘새 제보 작성하기’로 다시 시작
```

- **이전**: 어느 단계에서든 이전 버튼으로 돌아갈 수 있고, 입력·선택한 값은 그대로 남습니다. 고친 값은 확인 화면에서 목록을 다시 만들 때 반영됩니다.
- **오류**: 필수값이 비거나 형식이 틀리면 다음 단계로 넘어가지 않고, 문제가 있는 항목 아래에 이유와 고치는 방법을 적습니다.
- **다시 시작**: 상단 ‘처음부터 다시 시작’이나 완료 화면의 ‘새 제보 작성하기’를 누르면 입력·선택·오류·진행 상태가 모두 처음으로 돌아갑니다.

## 인터랙션 시나리오

행동 → 이벤트 → 조건 → 화면 반응 → 다음 상태로 정리했습니다.

| # | 행동 | 이벤트 | 조건 | 화면 반응 | 다음 상태 |
| --- | --- | --- | --- | --- | --- |
| 1 | ‘제보 시작하기’ 누름 | `click` | 항상 | 흐름 화면이 열리고 시작 버튼이 사라짐, 진행 표시 `1 / 3 · 물건 정보` | 1단계 |
| 2 | 1단계에서 ‘장소·연락 입력하기’ 누름 | `click` | 종류·분류·특징 중 하나라도 비어 있음 | 빈 항목마다 빨간 테두리와 안내 문구, 상단에 `확인이 필요한 항목이 N개`, 첫 빈 항목으로 포커스 | 1단계 유지 |
| 3 | 빈 항목을 채우거나 고름 | `input` / `change` | 해당 항목에 오류가 표시돼 있음 | 그 항목의 오류만 바로 사라지고, 모두 고치면 단계 안내도 사라짐 | 1단계 유지 |
| 4 | 물건 특징 입력 | `input` | 항상 | 글자 수 `N / 30`, 25자 이상이면 빨간 글자 | 1단계 유지 |
| 5 | 1단계에서 ‘장소·연락 입력하기’ 누름 | `click` | 필수값 모두 입력됨 | 2단계 표시, 진행 표시 `2 / 3 · 장소·연락` | 2단계 |
| 6 | 제보 종류를 ‘주웠어요’로 고름 | `change` | 습득 선택 | ‘맡겨 둔 곳’ 필수 칸이 나타나고, 날짜 문구가 ‘주운 날짜’로 바뀜(분실이면 숨김·‘잃어버린 날짜’) | 같은 단계 |
| 7 | 2단계에서 ‘제보 내용 확인하기’ 누름 (또는 입력창에서 Enter) | `click` / `keydown` | 건물·날짜·이메일(·맡겨 둔 곳)이 비었거나, 날짜가 오늘 이후이거나, 이메일 형식이 틀림 | 항목별 안내(예: `오늘 이후 날짜는 고를 수 없어요`, `이메일에는 @가 들어가야 해요`) | 2단계 유지 |
| 8 | 2단계에서 ‘제보 내용 확인하기’ 누름 | `click` | 모두 통과 | 3단계 표시, 입력값 목록 생성, 진행 표시 `3 / 3 · 제보 확인` | 3단계 |
| 9 | ‘장소·연락 수정하기’ / ‘물건 정보 수정하기’ 누름 | `click` | 항상 | 앞 단계로 이동, 입력한 값이 그대로 남아 있음 | 2단계 / 1단계 |
| 10 | 확인 화면에서 항목 옆 ‘수정’ 누름 | `click` | 항상 | 그 항목이 있는 단계로 이동 | 1단계 또는 2단계 |
| 11 | 값을 고치고 다시 확인 단계로 이동 | `click` | 필수값 통과 | 확인 목록에 고친 값이 반영됨 | 3단계 |
| 12 | ‘제보 완료하기’ 누름 | `click` | 1·2단계 값이 모두 유효함 | 접수번호·접수 문구(학교 메일 `.ac.kr`이면 문구 다름), 입력 요약, 초록색 완료 화면, 진행 표시 `제보 완료` | 완료 |
| 13 | ‘새 제보 작성하기’ 또는 ‘처음부터 다시 시작’ 누름 | `click` | 항상 | 모든 입력·선택·오류 문구·요약·완료 표시가 지워지고 1단계로 돌아감, 글자 수 `0 / 30` | 1단계(빈 상태) |

## 구현 방법

- `index.html`: 헤더 메뉴에 ‘단계별 제보’를 추가하고, `#flow` 구역에 시작 버튼과 단계 4개(`.flow-step`, `data-step`)를 만들었습니다. 모든 입력창에는 보이는 `label`을 두었고, 오류 문구는 `aria-describedby`로 입력창과 연결했습니다.
- `style.css`: 진행 단계 표시, 오류 상태, 확인 목록, 완료 상태, 768px 이하 한 열 배치, 어두운 테마를 추가했습니다. 기존 스타일은 지우지 않았습니다.
- `script.js`: 단계 전환(`showFlowStep`), 단계별 필수값 검사(`checkFlowStep`), 오류 표시·제거, 확인 목록 생성(`fillSummary`), 다시 시작(`handleFlowRestart`)을 추가했습니다. 입력값은 단계를 숨기기만 하고 지우지 않아 이전 단계로 돌아가도 유지됩니다. 접수 문구는 기존 `makeReportMessage()`를 재사용하고, 접수 수(`reportCount`)는 빠른 제보와 함께 이번 방문 동안 이어집니다.

## 7주차 수정 기록

**바꾼 내용**
기존에는 이메일과 물건 특징만 남기는 한 장짜리 폼이라 어디까지 입력했는지, 맞게 입력했는지 확인할 수 없었습니다. 제보를 4단계 흐름으로 나누어 단계별 필수 입력 검사, 확인 화면, 완료 화면, 다시 시작을 연결했습니다. 기존 빠른 제보는 간단히 남기고 싶은 사용자를 위해 그대로 두었습니다.

**이유와 사용자 이점**
- 한 번에 입력할 양이 줄고, 진행 표시(`N / 3`)로 남은 단계를 알 수 있습니다.
- 빠진 항목이 있으면 어디를 어떻게 고칠지 바로 보이고, 이전 단계로 돌아가도 입력이 사라지지 않습니다.
- 완료 전에 내용을 한 번 더 확인할 수 있고, 완료 화면의 접수번호로 제보가 끝났음을 확신할 수 있습니다.

## 2~6주차 수정 기록

### 구현하면서 바꾼 구조와 변경 이유

1. **1주차 `h1 + p`를 `header`로 이동**  
   서비스 이름과 한 줄 소개는 페이지 전체를 대표하는 정보이므로, 본문과 섞지 않고 맨 위 영역에 둡니다.

2. **본문을 `main`과 네 개의 `section`으로 나눔**  
   소개 → 기능 → 이용 방법 → 제보는 서로 다른 목적이므로, 같은 덩어리처럼 보이지 않게 구역을 나눕니다. 이 순서는 `<body>` 첫 줄 UX 계획 주석과 같게 맞췄습니다.

3. **마지막 영역 id를 `subscribe` 대신 `report`로 사용**  
   교안 예제는 소식 받기(`#subscribe`)입니다. 이 서비스의 핵심 행동은 이메일로 분실·습득을 **제보**하는 것이라, 메뉴 문구·제목·`id`를 같은 의미로 맞췄습니다.

4. **주요 기능은 `ul`, 이용 방법은 `ol`**  
   세 기능은 순서를 바꿔도 의미가 유지됩니다. 이용 방법은 제보를 보내기까지의 단계이므로 번호를 유지합니다.

5. **입력 영역의 버튼 문구를 `제보 보내기`로 변경**  
   버튼을 눌렀을 때 기대되는 결과가 드러나도록, 소식 신청이 아니라 제보 제출로 적었습니다. 이번 주에는 전송 기능은 없고 구조만 만듭니다.

6. **`style.css`, `script.js`는 수정하지 않음**  
   2주차는 HTML 구조가 과제 범위입니다.

### 직접 구현한 페이지와 AI 공통 예제의 비교

교안 완성 예제(공통 템플릿)와 이 저장소의 `index.html`을 같은 기준으로 비교했습니다.

| 기준 | 교안 공통 예제 | 이 페이지 |
| --- | --- | --- |
| 정보 계층 | `h1` 나의 서비스, 기능명도 빠른 시작·쉬운 사용처럼 일반 문구 | `h1` 캠퍼스 분실물 하나. `h2`는 구역, `h3`는 분실 제보·습득 등록처럼 기능 이름 |
| 시맨틱 구조 | `header` / `nav` / `main` / `section` / `footer`는 같음. 마지막 `section` id가 `subscribe` | 같은 뼈대. 핵심 행동에 맞게 마지막 구역을 `section#report`로 바꿈 |
| 접근성 | `nav aria-label`, `label for`와 `input id` 연결, `img alt`는 있음. alt가 “모바일로 서비스를 이용하는 사용자”처럼 범용 | 메뉴 이름과 `href`/`id`가 `report`로 일치. alt는 분실물 보관소 창구 장면처럼 이 위치의 의미를 적음 |

AI가 예제만 채워 넣으면 서비스 이름만 바뀌고 `#subscribe`·소식 신청 버튼이 남는 경우가 많습니다. 여기서는 핵심 행동(제보)과 구역 이름·링크·버튼을 같은 말로 맞추는 쪽을 택했습니다.

### 3주차 CSS 수정 기록

**수정한 내용**
주요 기능 목록(`.feature-list`)에 `display: flex`와 `gap: 20px`를 적용하고, 각 항목(`.feature-card`)에 `padding`과 `background-color`를 주어 카드 형태로 묶었습니다.

**수정 이유**
세로로 나열된 `ul` 목록만으로는 세 기능이 같은 종류의 정보라는 것이 한눈에 드러나지 않았습니다. 가로 배치와 카드 배경으로 묶어 세 기능을 동시에 비교할 수 있게 했습니다.

| 바꾼 속성 | 화면 변화 | 사용자 이점 |
| --- | --- | --- |
| `display:flex` · `gap` (`.feature-list`), `padding` · `background-color` (`.feature-card`) | 세 기능이 같은 간격의 카드로 한 줄에 배치됨 | 기능들이 같은 그룹임을 바로 인식하고 서로 비교하기 쉬워짐 |

### 4주차 반응형 수정 기록

**확인한 문제**
3주차 화면은 넓은 화면 기준으로 만들어, 390px(모바일 너비)에서 메뉴가 한 줄에 몰리고 서비스 소개의 글과 이미지가 가로로 끼면서 글자가 한 글자씩 줄바꿈되었습니다. 기능 카드도 폭이 좁아지면 글이 지나치게 눌렸습니다.

**수정한 내용**
`.site-nav`에 `flex-wrap: wrap`을 추가하고, `.feature-list`를 `display: flex`에서 `grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))` 자동 Grid로 바꿨습니다. 768px 이하 미디어 쿼리를 새로 작성해 메뉴·기능 카드·서비스 소개(`.about-layout`)·제보 폼(`.report-form`)을 한 열로 배치했습니다.

**달라진 점**
1100px·769px·768px·390px 네 너비에서 직접 확인한 결과, 768px 이하에서는 메뉴와 카드·폼이 세로 한 열로 바뀌고, 390px에서도 가로 스크롤이나 글자 잘림 없이 모든 내용을 읽고 입력할 수 있습니다.

| 바꾼 속성 | 화면 변화 | 사용자 이점 |
| --- | --- | --- |
| `.feature-list`를 Grid(`auto-fit`, `minmax`)로 교체, `@media (max-width: 768px)`로 메뉴·카드·폼을 한 열로 전환 | 화면이 좁아질수록 카드가 자동으로 줄어든 열로 재배치되고, 768px 이하에서는 메뉴·카드·입력창이 세로로 쌓임 | 모바일에서도 가로 스크롤 없이 내용을 읽고 분실·습득 제보를 입력할 수 있음 |

### 5주차 JavaScript 수정 기록

**추가한 기능**
분실·습득 제보 폼에서 이메일을 확인하고, 처리 결과를 안내 문구·스타일·버튼 상태로 보여 줍니다. 서버가 없어 실제 전송은 하지 않고 화면 반응만 구현했습니다.

**수정한 내용**
- `index.html`: body 끝에 `script.js`를 연결하고, 폼에 `novalidate`, 버튼 `id="reportButton"`, 안내 문구 `<p id="reportMessage" role="status">`를 추가했습니다.
- `script.js`: `const`(고정 문구·정규식)와 `let`(`isReported`, `reportCount`)로 값을 저장하고, `querySelector`로 요소를 고릅니다. `checkEmail()`과 `makeReportMessage()`가 `===`와 `if`로 입력값에 맞는 문구를 `return`하고, 버튼의 `click` 이벤트에 `sendReport()`를 연결했습니다. 연결 확인과 자료형 확인은 Console에 출력합니다.
- `style.css`: 오류(`is-error`)·완료(`is-success`) 상태 색과 비활성 버튼(`:disabled`) 스타일을 추가했습니다.

| 입력·상태 | 안내 문구 | 화면 변화 |
| --- | --- | --- |
| 빈 값 | 이메일을 입력해 주세요. | 빨간 문구, 입력창 빨간 테두리, 입력창으로 포커스 이동 |
| `@` 없음 | 이메일에는 @가 들어가야 해요. | 같음 |
| `a@b`처럼 형식이 틀림 | 이메일 형식을 확인해 주세요. | 같음 |
| 학교 메일(`.ac.kr`) | N번째 제보가 접수되었습니다. 학교 메일로 연락드릴게요. | 초록 배경 문구, 버튼 `접수 완료`(회색, 비활성) |
| 그 외 메일 | N번째 제보가 접수되었습니다. 입력하신 메일로 연락드릴게요. | 같음 |

접수 뒤 이메일을 고치면 버튼이 다시 켜져 새 제보를 보낼 수 있습니다.

**이유와 사용자 이점**
기존에는 버튼을 눌러도 아무 반응이 없어 제보가 됐는지 알 수 없었습니다. 잘못된 입력은 이유를 바로 알려 주고, 접수되면 문구·색·버튼이 함께 바뀌어 완료를 확신할 수 있으며, 비활성 버튼이 중복 제출을 막습니다.

**확인한 내용**
1100px(PC)와 390px(모바일)에서 위 상태를 모두 눌러 확인했습니다. Enter 키 제출도 동작하고, 가로 스크롤과 Console 오류는 없습니다.

### 6주차 이벤트와 동적 UI 수정 기록

5주차 제보 폼과 `script.js`에 이어서 같은 `index.html`, `style.css`, `script.js`를 수정했습니다. 새 프로젝트는 만들지 않았습니다.

#### 구현한 이벤트와 화면 변화

| 이벤트 | 연결한 요소 | 사용자 행동 | 함께 바뀌는 화면 (두 가지 이상) |
| --- | --- | --- | --- |
| `click` | `#themeButton` | 헤더의 테마 버튼 클릭 | 버튼 문구(어두운/밝은 테마로 바꾸기) + `body.dark` 클래스로 전체 색 + `aria-pressed` |
| `click` | `#reportButton` (5주차) | 제보 보내기 클릭 | 안내 문구 + 입력창 오류·성공 스타일 + 버튼 `접수 완료`·비활성 |
| `input` | `#itemInfo` | 물건 특징 입력·삭제 | 글자 수 문구(`N / 30`) + 25자 이상이면 빨간 글자(`is-near-limit`). 접수 뒤 고치면 버튼 다시 활성 |
| `input` | `#email` (5주차) | 이메일 수정 | 접수 뒤 수정하면 버튼 문구·활성 상태·안내 문구 복귀 |
| `change` | `#reportType` | 제보 종류를 분실↔습득으로 선택 | 버튼 문구(분실 제보 보내기/습득 등록하기) + 버튼 색(습득은 초록) + 안내 문구 + 입력 예시(placeholder) |

**탭 3개 (주요 기능)**
기존 `ul` 카드 3개(분실 제보·습득 등록·건물별 모아보기)를 같은 이름의 탭 3개로 바꿨습니다. 탭 버튼의 `data-target`이 패널 `id`와 연결되고, 탭을 누르면 `querySelectorAll()`과 `forEach()`로 모든 탭·패널의 선택을 해제한 뒤 누른 탭의 `is-active`·`aria-selected="true"`와 연결된 패널 하나만 `hidden`을 풀어 보여 줍니다. 선택된 탭은 보라색 글자·테두리·아래 굵은 선으로 구분됩니다. 제보 내용이 접수된 상태에서 제보 종류를 바꾸면 새 제보로 보고 버튼이 다시 켜집니다.

**수정한 파일**
- `index.html`: 헤더에 테마 버튼, `#features`를 `role="tablist"` 탭과 `role="tabpanel"` 패널로 변경, 제보 폼에 제보 종류 `select`와 물건 특징 입력창·글자 수 추가
- `style.css`: 탭·패널, 글자 수 경고, 습득 버튼 색, 어두운 테마(`body.dark`), 768px 이하 탭 세로 배치 추가. 사용하지 않게 된 `.feature-list`·`.feature-card`는 삭제
- `script.js`: 위 이벤트 함수와 탭 전환 함수 추가. 제보 보내기 때 물건 특징이 비어 있으면 안내하고, 접수 문구에 분실·습득 종류를 넣음
